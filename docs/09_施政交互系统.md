# 09 — 施政交互系统设计

> v1.0 — 已实现
>
> 本文档描述施政决策的两种交互范式，以及「玩家自创施政选项」的完整生命周期。

---

## 1. 概述

当前施政系统（税率调整 + 基础建设投资）以纯手动点击方式运行，交互直白但缺乏沉浸感和策略引导。

本次设计在原有手动施政的基础上，增加 **对话施政** 入口，并引入 **自创施政选项** 机制——玩家可通过与幕僚对话提出官方投资列表之外的施政构想，交由省布政司裁定后落地为可执行选项。

### 两种施政入口并存

| 入口 | 名称 | 适合场景 |
|------|------|---------|
| 现有 | **手动施政** | 快速执行已知动作，熟悉玩家常用 |
| 新增 | **对话施政** | 征求建议、探索新思路、新手引导 |

两者共享同一套底层执行逻辑（`InvestmentService.execute`），区别仅在触发路径。

界面变化：

- 自创选项：追加在列表底部，标注 `[新增]` 标签，样式上有视觉区分

## 3. 对话施政

### 3.1 入口与界面

对话施政与现有事件对话使用**同一入口面板**，但在面板顶部标明参与者角色。

> 注意：现有事件对话（如谈判、审案）是双人或专项对话；幕僚商议是**三人群聊**，界面需区分两种模式下的参与者列表。

入口位置：施政页新增「幕僚商议」按钮，点击打开对话面板，自动切换至三人群聊模式。

**群聊参与者（固定三人）**：
- 知县（玩家）
- 师爷（策略顾问，善谋划、懂时政）
- 县丞（执行顾问，熟悉本县财政、基建状况）

**消息气泡展示**：
- 系统消息（背景信息、提示）：居中浅色
- 幕僚发言：左侧气泡，附人名与头像占位
- 知县（玩家）发言：右侧气泡
- 施政建议卡片（见 §3.3）：独立卡片样式，在气泡流中内联显示

### 3.2 幕僚主动发言规则

幕僚在**以下条件满足时**会主动在群聊发出一条提醒消息（每回合最多触发一次）：

- 民心 < 40：师爷建议提升民心相关的已有施政（如资助村塾、赈灾）
- 治安 < 40：县丞建议增设衙役或修缮道路
- 商业 < 40：师爷建议修缮道路
- 文教 < 40：县丞建议扩建县学或资助村塾

**约束**：
- 主动建议只涉及**已有标准施政选项**，不提新构想
- 若当前资金不足以执行该建议，改为提示「目前财力有限，宜待秋收后再行考虑」
- 触发时机为玩家打开面板时（而非后台轮询），不需要 WebSocket

### 3.3 对话流程（玩家发起）

```
玩家发问 / 描述诉求
    ↓
师爷 or 县丞 给出文字建议（可多轮对话）
    ↓
LLM 后台识别建议中包含的可执行施政意图
    ↓
若为已有标准选项 → 插入「施政建议卡片」（§3.4）
若为非常规构想   → 插入「新建施政申报卡片」（§4.2）
    ↓
知县点击对应卡片按钮处理
```

### 3.4 施政建议卡片（标准选项）

```
┌─────────────────────────────────────────┐
│  施政建议                                │
│ 动作：修建水利（升至2级）                  │
│ 花费：约 240 两  │ 工期：12 个月           │
│ 预期效果：全县农业产出 +15%               │
│                                         │
│   点击卡片主体 → 立即执行   × → 静默忽略  │
└─────────────────────────────────────────┘
```

字段说明：
- 动作名称、花费、工期 来自 `InvestmentService.get_available_actions()` 实时计算
- 若该动作当前不可用（资金不足、已在建等），「确认执行」置灰并显示原因
- 需要指定目标村庄的动作（如开垦荒地、资助村塾），系统自动选择最优村庄（开垦优先选安全村，资助村塾优先选无学校的人口最多村），结果显示于系统消息中

### 3.5 意图识别机制

LLM 返回时要求结构化输出，包含两部分：
1. **自然语言回复**（展示给玩家）
2. **意图数组**（后台解析，不展示）

```json
{
  "reply": "县丞以为，眼下水利年久失修，若能在今冬枯水期动工升至二级...",
  "suggested_actions": [
    {
      "action": "build_irrigation",
      "is_standard": true,
      "target_village": null,
      "rationale": "提升农业产出，减少旱灾损失"
    }
  ],
  "proposed_policies": [
    {
      "name": "新建集市",
      "is_standard": false,
      "rationale": "商业低迷，增加集市可改善"
    }
  ]
}
```

- `suggested_actions`（`is_standard: true`）：每项对应一张标准施政建议卡片
- `proposed_policies`（`is_standard: false`）：每项对应一张新建施政申报卡片（见 §4.2）

### 3.6 NPC 性格与建议倾向

师爷/县丞的对话性格**与现有 Agent 系统中的 NPC 属性绑定**，在系统 prompt 中注入：

```python
# 从 game.agents 中取本游戏的师爷/县丞 Agent 记录
# 注入属性：personality, ideology, goals, player_affinity
COUNSEL_SYSTEM_PROMPT = """
你扮演{name}，担任知县的{role}。
性格：{personality_desc}
政治倾向：{ideology_desc}
个人目标：{goals}
当前对知县的好感度：{player_affinity}/100

行为指引：
- 好感度 < 40：建议偏保守，措辞疏远，可能刻意回避有利于知县清名的方案
- 好感度 40-70：中性专业建议
- 好感度 > 70：主动提供更多信息，支持知县长远利益
- 若 ideology.pragmatic_vs_idealist 偏功利：倾向推荐短期见效快的施政
- 若 ideology.reform_vs_tradition 偏保守：倾向推荐修缮维护类，不鼓励新建
"""
```

### 3.7 与手动施政的关系

- 对话施政执行的动作与手动施政完全等价，不存在独立的「行动点」限制
- 同一动作可在两个入口触发，`InvestmentService.validate()` 统一处理合法性
- 对话记录**不跨回合持久化**（关闭面板后消失），仅用于当回合决策辅助

## 4. 自创施政选项

### 4.1 概述

对于 `INVESTMENT_TYPES` 之外的施政构想，玩家可通过对话提出，提交省布政司审核，下一回合获得带成本/收益的新施政选项。

**三阶段流程**：提出 → 审核（下一个月） → 落地

### 4.2 阶段一：提出申请

触发来源：LLM 回复中的 `proposed_policies` 字段，或玩家在对话中直接描述非常规构想时由 LLM 识别。

群聊中插入「新建施政申报卡片」：

```
┌─────────────────────────────────────────┐
│  新建施政构想                             │
│ 「新建集市」                              │
│ 此举非常规，需报请省布政司核准方可执行。    │
│                                         │
│   [申报省布政司]      [暂不考虑]           │
└─────────────────────────────────────────┘
```

点击「申报省布政司」后：
- 创建 `ProposedPolicy` 记录（status=PENDING）
- 群聊插入系统消息：「已向省布政司递交申请，请等候下月批复。」
- **同一回合内**不可重复申请相同构想名称（前端+后端双重校验）

**重复申请规则（同一 game）**：
- 若某构想已被批准（APPROVED），不可重复申请
- 若某构想已被拒绝（REJECTED），拒绝后 **6 个月**内提交相同或高度相似构想时，省布政使将直接拒绝（带说明），不重新进行完整审核
- 「相似」判断由省布政使 LLM 在审核时自行识别，不做关键词硬匹配

### 4.3 阶段二：省布政使 AI 审核

**触发时机**：下一次月度结算（`SettlementService.advance_season()`）末尾，对本 game 所有 PENDING 记录**批量处理**，统一调用一次 LLM（传入多个申请，返回对应多个批复）。

**省布政使 Persona**（无独立 Agent 记录，LLM 临时角色）：

```python
PROVINCIAL_GOVERNOR_PROMPT = """
你是大明{province_name}省布政使，负责裁定各县非常规施政申请。
职责：在维护财政平衡的前提下，对县令提出的施政构想给出合理的成本与收益。

参考标准（现有施政选项）：
{existing_policies_summary}

申请县当前状况：
{county_snapshot}

本次待审申请列表：
{proposals_json}

裁定要求：
- 若批准：给出花费（两）、工期（月）、预期效果（指标变化量），裁定一锤定音，不议价
- 若拒绝：给出简短理由（需有官方措辞风格）
- 效果幅度应与现有施政选项保持平衡，不可过强或过廉
- 若某申请与6个月内已拒申请高度相似，直接拒绝并注明
"""
```

输出（结构化数组，与输入申请一一对应）：

```json
[
  {
    "proposal_id": 42,
    "approved": true,
    "policy_name": "新建集市",
    "action_key": "build_new_market",
    "cost": 120,
    "delay_months": 3,
    "effects_data": {
      "immediate": { "commercial": 15 },
      "add_market": { "merchants": 10 },
      "description": "新增集市一处，商业+15，商户容量+10"
    },
    "rationale": "该县商业底子尚可，新建集市可带动税收，成本适中，准予备案。"
  },
  {
    "proposal_id": 43,
    "approved": false,
    "rationale": "建设农业技术研究站耗资巨大，与本县财力不符，暂不予批准。"
  }
]
```

### 4.4 阶段三：落地与展示

批准后，新选项出现在以下三处：

**① 手动施政面板（「新增」区域）**
- 列表末尾追加，标注 `[新增]` 标签
- 展示形式与标准选项相同（名称、花费、效果、可用性）
- 通过 `ProposedPolicy`（status=APPROVED）动态加载，不硬编码进代码

**② 本县对话施政群聊（系统通知）**
- 结算完成后，玩家下次打开面板时显示系统消息：
  > 「省布政司已批复：准予在本县试行「新建集市」，花费 120 两，建成后商业+15。请县尊裁定是否执行。」
- 消息后附施政建议卡片（同 §3.4），可直接确认执行

**③ 邻县同步（批复后立即同步）**

同步规则：
- 批复通过后，在本对局内同父 `AdminUnit` 的其他县自动创建关联的 `ProposedPolicy` 记录（status=APPROVED，`synced_from` 指向原记录）
- 同步的是**选项定义**（名称、成本、效果），不是执行决定
- 邻县玩家知县在手动施政「新增」区域可见该选项，也会在下次打开群聊时收到通知
- **AI 邻县知县不会主动执行新增选项**（人工选择权在玩家知县）
- 知府游戏中，邻县新增选项**不自动出现在知府视角**（知府视角暂不支持）
- 新开对局不继承历史对局的自创选项（`ProposedPolicy` 与 `GameState` 绑定）

### 4.5 执行路径

自创选项执行时，通过扩展后的投资接口统一处理：
- `action_key` 查找对应的 `ProposedPolicy`（而非 `INVESTMENT_TYPES`）
- 扣款、加入 `active_investments`、记录 `EventLog`（同标准流程）
- 结算时 `SettlementService` 按 `effects_data` 字段动态 apply（通用效果引擎）

## 5. 数据模型

### 5.1 ProposedPolicy（自创施政选项）

```python
class ProposedPolicy(models.Model):
    class Status(models.TextChoices):
        PENDING   = 'PENDING',  '待审核'
        APPROVED  = 'APPROVED', '已批准'
        REJECTED  = 'REJECTED', '已拒绝'
        ARCHIVED  = 'ARCHIVED', '管理员归档（不采纳）'
        PROMOTED  = 'PROMOTED', '已提升为标准选项'

    game             = models.ForeignKey('GameState', on_delete=models.CASCADE,
                           related_name='proposed_policies')
    proposer         = models.CharField(max_length=50)       # '知县' / '师爷' / '县丞'
    raw_proposal     = models.TextField()                    # 原始申请描述
    policy_name      = models.CharField(max_length=100)
    action_key       = models.CharField(max_length=100, blank=True)  # 审核后填入
    status           = models.CharField(max_length=20, choices=Status.choices,
                           default=Status.PENDING)
    cost             = models.IntegerField(null=True)
    delay_months     = models.IntegerField(null=True)
    effects_data     = models.JSONField(default=dict)        # 效果定义（见 §5.2）
    rationale        = models.TextField(blank=True)          # 布政使批复原文
    rejection_reason = models.TextField(blank=True)
    synced_from      = models.ForeignKey(                    # 邻县同步时指向原始记录
        'self', null=True, blank=True,
        related_name='synced_copies',
        on_delete=models.SET_NULL
    )
    is_executed      = models.BooleanField(default=False)    # 本县是否已执行
    created_at       = models.DateTimeField(auto_now_add=True)
    reviewed_at      = models.DateTimeField(null=True)       # 布政使批复时间
    rejected_at      = models.DateTimeField(null=True)       # 用于6个月冷却计算
```

### 5.2 StandardPolicy（标准施政选项，数据库级）

> 设计要点：此表是 `InvestmentService.INVESTMENT_TYPES` 的数据库扩展，运行时合并加载。
> 初始为空，只有管理员提升后才写入记录。需要谨慎设计——已有对局不受此表影响，仅新开对局加载。

```python
class StandardPolicy(models.Model):
    """
    管理员从 ProposedPolicy 提升而来的全局标准施政选项。
    新对局的 InvestmentService 初始化时合并此表与内置 INVESTMENT_TYPES。
    """
    action_key       = models.CharField(max_length=100, unique=True)
    policy_name      = models.CharField(max_length=100)
    cost_base        = models.IntegerField()                 # 基准花费（两），乘以 price_index
    delay_months     = models.IntegerField()
    requires_village = models.BooleanField(default=False)
    effects_data     = models.JSONField(default=dict)        # 同 ProposedPolicy.effects_data 格式
    description      = models.TextField(blank=True)          # 简述（用于投资面板展示）
    source_policy    = models.ForeignKey(                    # 来源 ProposedPolicy
        ProposedPolicy, null=True, blank=True,
        on_delete=models.SET_NULL
    )
    is_active        = models.BooleanField(default=True)     # 可由管理员临时停用
    promoted_at      = models.DateTimeField(auto_now_add=True)
    promoted_by      = models.CharField(max_length=100)      # 操作管理员用户名
    notes            = models.TextField(blank=True)          # 管理员备注

    class Meta:
        verbose_name = '标准施政选项'
```

> **注意**：`StandardPolicy` 引入后，`InvestmentService.get_available_actions()` 需要改为同时查询此表（过滤 `is_active=True`），合并进结果列表。成本计算方式与内置选项相同（`cost_base × price_index`）。

### 5.3 通用效果引擎（effects_data 格式）

```json
{
  "immediate": {
    "commercial": 15,
    "morale": 3
  },
  "on_complete": {
    "add_market": { "merchants": 10 }
  },
  "monthly": {},
  "description": "新增集市一处，商业+15，商户容量+10"
}
```

效果字段说明：
- `immediate`：执行（扣款）时立即应用的指标 delta
- `on_complete`：工期结束时应用（加入 `active_investments`，结算时检查）
- `add_market`：特殊操作，向 `county.markets` 追加集市记录
- `monthly`：每月持续效果（暂保留，v1 不实现）

## 6. 管理员功能

### 6.1 页面入口

Django Admin 扩展：

| 路径 | 说明 |
|------|------|
| `/admin/game/proposedpolicy/` | 查看/管理自创选项（所有对局） |
| `/admin/game/standardpolicy/` | 查看/管理已提升的标准选项 |

### 6.2 ProposedPolicy Admin 功能

| 功能 | 描述 |
|------|------|
| 列表视图 | 按 status / game / created_at 过滤；展示 policy_name、rationale、is_executed |
| 执行统计 | 某选项在多少对局被创建 / 被执行（`is_executed=True` 计数） |
| 提升为标准选项 | Admin Action：`promote_to_standard` |
| 归档 | Admin Action：将 status 改为 ARCHIVED，附管理员备注 |

**提升流程（`promote_to_standard` Action）**：
1. 校验 `status == APPROVED` 且 `action_key` 不与现有 `StandardPolicy` 冲突
2. 创建 `StandardPolicy` 记录，`source_policy` 指向本记录
3. 将本 `ProposedPolicy` status 更新为 `PROMOTED`
4. **不影响**任何现有对局（现有对局继续用自己的 `ProposedPolicy` 记录执行）
5. Admin 界面展示提示：「已提升，将在新对局中生效」

### 6.3 StandardPolicy Admin 功能

| 功能 | 描述 |
|------|------|
| 列表视图 | 展示 action_key、policy_name、cost_base、is_active、promoted_at |
| 停用/启用 | 切换 `is_active`，即时生效（新对局加载时不再包含） |
| 编辑 | 可调整 cost_base、effects_data（需谨慎，已有对局不受影响） |

## 7. 技术实现要点

### 7.1 后端接口（新增）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/games/{id}/counsel/message/` | 发送对话消息，返回幕僚回复 + 卡片列表 |
| POST | `/api/games/{id}/counsel/propose/` | 提交自创施政申请，创建 ProposedPolicy(PENDING) |
| GET  | `/api/games/{id}/counsel/policies/` | 获取本对局自创选项列表（含状态） |
| GET  | `/api/games/{id}/counsel/pending-notifications/` | 获取结算后待展示的批复通知（用于打开面板时回显） |

现有接口扩展：
- `POST /api/games/{id}/invest/` 兼容自创选项的 `action_key`（查 `ProposedPolicy` 而非 `INVESTMENT_TYPES`）
- `GET /api/games/{id}/available-actions/` 合并返回标准选项 + `StandardPolicy` + 本局批准的 `ProposedPolicy`

### 7.2 结算流程新增步骤

在 `SettlementService.advance_season()` 末尾追加：

```python
# 审核本局待审的自创施政申请
PolicyReviewService.review_pending_proposals(game)
# 同步已批准选项至邻县
PolicySyncService.sync_approved_to_neighbors(game)
```

### 7.3 前端新增组件

`components-counsel.js`（`Game.counsel` 命名空间）：
- `openCounselPanel()`：打开面板，加载待显示的批复通知，检查主动提醒条件
- `sendMessage(text)`：发送消息，渲染幕僚回复、标准卡片、申报卡片
- `renderActionCard(suggestedAction)`：渲染标准施政建议卡片
- `renderProposeCard(proposedPolicy)`：渲染新建施政申报卡片
- `confirmAction(actionKey, targetVillage)`：确认执行，调用 `Game.api.invest()`
- `submitProposal(proposalData)`：提交申报，调用 `Game.api.proposeCounselPolicy()`
- `renderBatchNotifications(policies)`：渲染批复通知（结算后首次打开面板时展示）

`api.js` 新增：
- `sendCounselMessage(gameId, text)`
- `proposeCounselPolicy(gameId, proposalData)`
- `getCounselPolicies(gameId)`
- `getCounselPendingNotifications(gameId)`

### 7.4 对话上下文管理

- 对话历史存储在**前端内存**（`Game.counsel.history`），不持久化到后端
- 每次 LLM 调用携带最近 **6 轮**对话历史
- 系统 prompt 携带当前县域状态快照：民心/治安/商业/文教/库存/在建项目/已批准自创选项列表
- 师爷/县丞 persona 从本局 `Agent` 记录中读取（`name`/`personality`/`ideology`/`player_affinity`）

## 8. 关键约束与边界

| 约束 | 描述 |
|------|------|
| 主动提醒触发条件 | 任意一项（民心/治安/商业/文教）< 40，且仅建议已有标准施政 |
| 自创申请冷却 | 被拒后同类构想 6 个月内布政使直接拒绝（LLM 判定相似度） |
| 邻县同步范围 | 仅同父 AdminUnit 下的其他县；知府视角不同步；AI 知县不主动执行 |
| AI 知县新增 | 不支持，仅玩家知县可提出自创申请 |
| 标准选项生效范围 | 仅对提升操作之后新开的对局生效，存量对局不受影响 |
| 布政使裁定 | 一锤定音，不提供议价或上诉机制 |
| 对话记录持久化 | 不持久化，关闭面板后消失；批复通知单独持久化（见 §7.1） |
