# 02c — 司法系统详细设计

> 状态：当前设计主稿
>
> 本文档用于替代旧版 `docs/09_司法审判系统_知府.md` 中已经不再适用的主流程设计。
> 新方案强调“县级先审，府级复审”，并与月度回合、县/州混合治理、AI/玩家双模式保持一致。

---

## 1. 设计目标

### 1.1 核心目标

司法系统不再只属于知府端的“直接抽案裁决”，而是改为一条更自然的行政流转链：

`原始卷宗池 → 本局实例化卷宗 → 县丞意见 → 知县处理 → 上呈知府 → 知府复审 → 考评沉淀`

目标有三点：

- 让知县玩法也真正参与司法，而不是只有知府端看见卷宗。
- 让知府看到的案件有明确来源：这些案件是下级州县审过、上呈过的案子。
- 让司法结果既影响即时指标，也影响对知县/知州的长期考评。

### 1.2 设计原则

- **月度回合统一**：游戏所有职位都以“每月一个回合”为基础。
- **县先府后**：司法案件先进入县/州审理，再进入府级复审。
- **模板不污染**：原始卷宗池保持不变，所有本地化内容只存在于本局实例中。
- **实例可追踪**：每个案件实例都能追溯模板来源、属地、角色替换、流转状态。
- **玩家与 AI 同规则**：玩家知县和 AI 知县走同一套案件流转规则，区别只在决策者是谁。
- **后台生成不阻塞主流程**：实例化卷宗采用后台预生成与惰性补齐机制，不阻塞前端推进。

## 2. 产品真相

### 2.1 哪些角色会接触司法系统

- **知县 / 知州**：在特定月份会出现县/州级司法 tab，处理本地待审案件。
- **知府**：在下一月接收下级已经上呈的案件，进行复审与终判。
- **巡抚及以上**：当前不纳入本系统第一阶段实现。

### 2.2 县与州是否共用一套流程

是。

- 州采用与县完全相同的司法流程。
- 差异只体现在规模与数值上，不单独设计另一套司法机制。

### 2.3 当前建议的司法窗口

为了与现有季度节点、知府司法节奏和月度推进保持一致，采用如下窗口：

- **县/州司法处理月**：`二月 / 五月 / 八月 / 冬月`
- **知府司法复审月**：`三月 / 六月 / 九月 / 腊月`

也就是说：

- 县/州在前一个月处理本地卷宗；
- 知府在下一个月处理由下级上呈的案件。

## 3. 总体流程

### 3.1 每局游戏开始后的后台准备

每个新游戏开始后，系统会在后台自动为本局所有州县生成“本局司法实例”。

生成来源仍然是原始卷宗池，但会进行本地化实例化：

- 替换属地为本局真实下辖县/州；
- 若卷宗中涉及地主、农民、佃户、证人等角色，则替换为本县/州下属村庄中的本地角色；
- 保留模板 ID，便于追踪与 debug；
- 生成后的实例只属于当前游戏，不回写原始模板池。

### 3.2 县/州阶段的案件处理

在县/州司法处理月，县/州端司法 tab 出现。

每个县/州会看到 **5 个本轮待审案件**。

对每个案件：

1. 默认已有一条 **县丞意见**；
2. 知县/知州可选择：
   - `维持原判`
   - `打回重审`
3. 若选择 `维持原判`：
   - 该案直接进入下个月知府司法池；
4. 若选择 `打回重审`：
   - 该案回到本县/州待审池；
   - 县丞会给出第二轮处理意见；
   - 第二轮时必须结案，不再允许继续打回。

### 3.3 第二轮规则

第二轮时，知县/知州不再拥有无限拖延空间，必须结案。

第二轮新增一个选项：

- `搁置委托上级裁定`

该选项表示：

- 本级长官认为自己无法稳妥裁定此案；
- 因此将案件搁置并委托上级（知府）直接裁定；
- 该行为会**轻微降低知县/知州的能力评价与声望**。

因此，第二轮的有效选项为：

- `维持原判`
- `搁置委托上级裁定`

第二轮不再允许再次 `打回重审`。

### 3.4 知府阶段

知府司法月时，知府看到的案件来源不再是“直接从模板池抽取”，而是：

- 上个月由各县/州 `维持原判` 上呈的案件；
- 或第二轮中选择 `搁置委托上级裁定` 的案件。

知府仍使用当前三种终判：

- `核准原判`
- `驳回重审`
- `提审改判`

知府终判后：

- 影响府级即时指标；
- 回写该县/州的司法履历；
- 纳入年终对知县/知州的考评素材。

## 4. 县/州端前端交互设计

### 4.1 司法 tab 的显示规则

县/州端司法 tab 只在司法处理月出现：

- 二月
- 五月
- 八月
- 冬月

若本轮案件尚未实例化完成，则显示：

- “卷宗整理中”
- 当前后台生成进度

### 4.2 每案展示内容

县/州端每案应展示：

- 案名
- 卷宗正文
- 附件与疑点
- 本地化后的属地
- 本地化后的村庄、地主、农民等涉案角色
- 县丞当前意见
- 县丞当前理由
- 当前轮次（第一轮 / 第二轮）

### 4.3 玩家可选动作

第一轮：

- `维持原判`
- `打回重审`

第二轮：

- `维持原判`
- `搁置委托上级裁定`

### 4.4 AI 知县 / 知州

AI 下属也走同一流程：

- 先接收县丞意见；
- 再决定是否维持、打回，或在第二轮委托上级；
- 只是不由前端玩家操作，而由后端自动推进。

## 5. 知府端前端交互设计

知府司法 tab 改为只显示“下级已上呈”的案件。

每个案件应附带以下上下文：

- 来源县/州
- 本地化卷宗正文
- 县丞最近一轮意见
- 知县/知州最终选择
- 是否经历过重审

知府看到的案件因此更具行政真实感：

- 不是“系统随机扔给你一案”；
- 而是“下级已经审理并上呈给你的案件”。

### 6.1 `JudicialCaseInstance`

表示“某局游戏中的一个本地化卷宗实例”。

建议字段：

- `game_id`
- `county_unit_id`
- `prefect_unit_id`
- `template_case_id`
- `county_review_season`
- `prefect_review_season`
- `status`
- `local_payload`
- `actor_map`
- `assistant_rounds`
- `magistrate_rounds`
- `submitted_to_prefect`
- `submitted_season`
- `prefect_decision`

### 6.2 `JudicialGenerationState`

表示“本局司法实例化后台任务状态”。

建议字段：

- `total_windows`
- `generated_windows`
- `last_error`
- `started_at`
- `finished_at`

## 7. 卷宗实例化机制

### 7.1 原始模板池

原始卷宗池保持不变，仍作为历史模板来源。

模板池不直接存本局属地，也不直接存本局人物。

### 7.2 本地化实例化

每个模板在实例化时要绑定：

- 本局真实州县
- 本州县真实村庄
- 本地化角色

### 7.3 角色替换要求

当模板中出现以下角色时，必须映射为本地角色：

- 地主
- 农民
- 佃户
- 证人
- 仓吏 / 书吏 / 衙役等基层官差

这些角色应来自当前州县下属村庄或县衙本地角色池，而不是继续沿用模板中的固定姓名。

### 7.4 实例数量建议

建议按“司法窗口”预生成，而不是把整个模板池一次性铺满。

建议基线：

- 每县/州每个司法窗口预生成 `5` 个案件

如果一局游戏有 5~8 个县州，则总量仍可控，也更利于调试与持久化。

---

## 8. 县丞意见机制

### 8.1 第一轮县丞意见

每个案件进入县/州司法 tab 时，默认已经有一条县丞意见：

- `维持原判`
- 或 `打回重审`

并附带理由。

### 8.2 第二轮县丞意见

若第一轮被知县/知州 `打回重审`：

- 案件继续保留在本县/州待审池；
- 县丞必须给出第二轮意见；
- 第二轮意见应当体现“重新审视后的不同判断”。

第二轮时，县丞可能：

- 给出与上一轮相反的意见；
- 或放弃明确判断。

### 8.3 县丞“放弃”后的命运

若县丞在第二轮中放弃明确判断，案件**不视为永久消失**。

规则为：

- 本轮不再继续处理；
- 该案可在**下个季度再次出现**。

这意味着司法积压是可能存在的，能增强行政真实感。

---

## 9. AI 决策职责划分

### 9.1 县丞

第一阶段建议：

- 县丞意见采用**规则生成**；
- 不优先接入 LLM。

原因：

- 县丞只是“建议层”；
- 规则生成更稳定、更容易调试、更容易约束两轮逻辑。

### 9.2 AI 知县 / 知州

AI 知县 / 知州可以使用 LLM 或规则模型来判断是否接受县丞意见。

但无论使用哪种方式，都必须遵守同一套流程约束：

- 第一轮可 `维持原判` 或 `打回重审`
- 第二轮必须结案
- 第二轮可 `维持原判` 或 `搁置委托上级裁定`

---

## 10. 知府终判与考评联动

知府终判后，影响不应只停留在即时指标。

还应写入下级州县的司法履历，用于年终考评。

建议沉淀内容：

- 本案是否被知府推翻
- 本案是否被驳回重审
- 本案是否由下级主动委托上级裁定
- 本案对该知县/知州能力信号的影响
- 本案对该知县/知州声望信号的影响

其中：

- 第二轮选择 `搁置委托上级裁定` 会轻微降低能力与声望；
- 被知府 `提审改判` 推翻，会明显不利于考评；
- 正确维持并被知府核准，可形成轻度正向信号。

---

## 11. 后台运行机制

### 11.1 为什么需要后台生成

实例化卷宗、替换角色、按窗口分配州县，属于相对重的准备工作。

若在“创建游戏”或“推进月份”的主请求里同步完成，容易拖慢前端响应。

### 11.2 建议机制

采用“后台线程 + 持久化进度 + 惰性补齐”的混合模式：

- 游戏创建后，通过后台任务启动司法实例化；
- 每完成一小批就持久化进度；
- 若后台中断，则在相关请求触发时按小预算补齐。

### 11.3 不阻塞前端的要求

系统不应因为司法实例化未完成而阻塞玩家推进月份。

若未完成：

- 县/州司法 tab 显示“卷宗整理中”；
- debug 页面显示当前实例化进度；
- 系统继续在后台补齐。

---

## 12. Debug 与后台查看

需要保留一个专门的后台调试页面 / API，用于查看本局司法实例数据。

该页面至少应能查看：

- 本局各县/州已实例化的案件
- 每案来自哪个模板
- 属地和村庄替换结果
- 本地角色映射
- 当前状态
- 县丞每轮意见
- 知县/知州选择
- 是否已经进入知府池
- 知府是否已终判

该 debug 页面属于开发 / 调试用途，不进入普通玩家主 UI。

---

## 13. 状态机建议

建议案件状态至少包括：

- `PENDING_ASSISTANT_REVIEW`
- `PENDING_MAGISTRATE_ROUND_1`
- `RETURNED_FOR_REVIEW`
- `PENDING_MAGISTRATE_ROUND_2`
- `SUBMITTED_TO_PREFECT`
- `DEFERRED_TO_PREFECT`
- `PREFECT_DECIDED`
- `WITHDRAWN_THIS_QUARTER`

其中：

- `WITHDRAWN_THIS_QUARTER` 表示本季度未继续处理，但下季度可再次出现；
- `DEFERRED_TO_PREFECT` 表示知县/知州明确搁置并委托上级裁定。

## 14. 第一阶段实现顺序

建议按下面顺序实施：

### 第一批：数据层与实例化

- 新增司法实例模型
- 新增生成状态模型
- 完成卷宗模板 → 本局实例化
- 完成后台生成与 debug 查看

### 第二批：县/州端司法 tab

- 县/州端司法页面
- 第一轮处理
- 第二轮处理
- `搁置委托上级裁定`

### 第三批：知府端来源改造

- 知府司法池只接收下级上呈案件
- 知府终判结果回写到州县司法履历

### 第四批：AI 接入

- AI 知县 / 知州自动处理县级司法
- 再视稳定性决定是否引入更强的 LLM 判断

## 15. 已确认规则

以下规则已经确认，后续实现按此为准：

- 第二轮必须结案，不允许再次打回重审。
- 第二轮新增 `搁置委托上级裁定`，会轻微降低知县/知州能力与声望。
- 县丞“放弃”后，案件不是永久消失，下个季度可能再次出现。
- 州完全沿用县的司法流程，不单独设计另一套。
